# 트러블슈팅 #001 — 처리 배치에서 같은 기사가 중복 처리되어 UNIQUE 제약 위반

- **날짜**: 2026-08-09
- **단계**: v1 (Claude 요약·분류 배치)
- **환경**: Spring Boot 4.1 / Spring Batch 6.0 / PostgreSQL 16 / JPA(Hibernate 7)
- **한 줄 요약**: 처리 배치의 커스텀 `ItemReader`가 "상태 기반 재조회" 방식이라, 아직 처리 전(PENDING) 기사를 다시 읽어 같은 기사를 한 청크에서 두 번 처리 → 요약 중복 INSERT로 UNIQUE 제약 위반.

---

## 1. 증상

처리 배치(`processingJob`)가 대량(약 100건) 처리는 잘 하다가, **PENDING이 소수만 남은 시점**에 실패.

```
org.springframework.dao.DataIntegrityViolationException:
  ERROR: duplicate key value violates unique constraint "uq_article_summary_raw"
  Detail: Key (raw_article_id)=(101) already exists.
  [insert into article_summary (...) values (?,?,?,?,?)]
  at com.jinsu.newspipeline.process.ProcessedArticleWriter.write(ProcessedArticleWriter.java:29)
```

- `article_summary`에는 `raw_article_id`에 UNIQUE 제약(`uq_article_summary_raw`)이 걸려 있음(기사 1건당 요약 1건 보장 = 멱등성 장치).
- 같은 `raw_article_id`(101)로 INSERT가 두 번 시도됨.

## 2. 데이터 무결성 확인 (피해 없음)

실패 직후 DB 상태:

| 확인 | 결과 |
|---|---|
| `article_summary` 행 수 | 100 |
| `raw_article_id` 중복 요약 행 | **0건** (UNIQUE 제약이 막음) |
| 101/102 상태 | `PENDING`, 요약 없음 (실패 청크 통째 롤백) |

→ **UNIQUE 제약이 잘못된 데이터를 막아준 덕에 DB는 깨끗.** 별도 정리 불필요. (제약을 안 걸었다면 조용히 중복 데이터가 쌓였을 것 — 제약의 가치를 실증)

## 3. 원인 분석

### 문제의 Reader (Before)

```java
// 버퍼가 비면 "PENDING 상위 50건"을 다시 조회
public RawArticle read() {
    if (buffer.isEmpty()) {
        buffer.addAll(repository.findTop50ByStatusOrderByIdAsc(PENDING));
    }
    return buffer.poll();
}
```

"처리된 기사는 DONE으로 바뀌어 PENDING 목록에서 빠지므로, 항상 첫 페이지만 다시 읽으면 안전하다"고 가정했다. **이 가정이 틀렸다.**

### 왜 틀렸나 — 읽기와 처리(커밋) 사이의 시간차

Spring Batch chunk 모델은 `read × N → process × N → write(commit)` 순서다.
**기사를 `read()`로 넘긴 시점엔 아직 processor/writer가 안 돌았으므로 상태가 PENDING 그대로**다.

버퍼 경계가 청크 중간에 걸리면 이런 일이 벌어진다 (chunk=5, 남은 PENDING=2 예시):

```
버퍼: [101, 102]
chunk가 5개를 원함 → read() 호출:
  read() → 101 반환 (buffer=[102])           ※101 아직 PENDING
  read() → 102 반환 (buffer=[])              ※102 아직 PENDING
  read() → buffer 비었으니 재조회
           findTop50ByStatus(PENDING) → [101, 102]  ← 아직 안 바뀜! 또 딸려옴
        → 101 반환                             ※같은 101 두 번째
  read() → 102 반환                             ※같은 102 두 번째
  read() → 재조회 → [101,102] → 101 반환        ※101 세 번째
청크 = [101, 102, 101, 102, 101]
→ process 후 write에서 101 요약을 두 번 INSERT → UNIQUE 위반 💥
```

대량 구간에서는 우연히 버퍼(50) 경계와 청크(5) 경계가 맞아떨어져 문제가 안 보이다가,
**남은 PENDING이 청크보다 적어지는 순간(꼬리 구간)** 반드시 재현됐다.

## 4. 해결 — 커서(keyset) 방식으로 전환

"상태로만 재조회"를 버리고, **이미 읽어 넘긴 id는 두 번 다시 안 읽도록** 커서(`id > lastId`)를 둔다.

### 수정된 Reader (After)

```java
private long lastId = 0L;   // @StepScope 라 실행마다 0으로 초기화

public RawArticle read() {
    if (buffer.isEmpty()) {
        buffer.addAll(
            repository.findTop50ByStatusAndIdGreaterThanOrderByIdAsc(PENDING, lastId));
    }
    RawArticle a = buffer.poll();
    if (a != null) {
        lastId = a.getId();   // 커서 전진: 이 id 이하는 다시 조회 안 함
    }
    return a;
}
```

- 재조회 시 `id > lastId` 조건이 **방금 넘겼지만 아직 커밋 안 된 PENDING 기사**를 걸러낸다.
- 커밋 타이밍과 무관하게 "한 번 넘긴 것은 다시 안 읽음"이 보장됨.
- `status = PENDING` 필터는 유지 → 이전 실행에서 이미 DONE/FAILED된 건은 건너뜀.
- 이 방식이 성립하는 전제: **id가 단조 증가**(append-only insert + DB 시퀀스/IDENTITY). → [관련 개념](#6-관련-개념--id-생성은-왜-maxid1이-아니라-시퀀스인가) 참고.

## 5. 검증

- 재시작 후 꼬리 구간(101·102) 재현 케이스에서 중복 에러 없이 `COMPLETED`.
- 이후 반복 실행에서도 새로 수집된 PENDING만 처리, 중복 없음.

## 6. 관련 개념 — id 생성은 왜 `MAX(id)+1`이 아니라 시퀀스인가

> "id 넣을 때 `MAX(id)+1`로 해야 하는 것 아니냐?"는 질문과 연결되는 부분.

이번 UNIQUE 위반은 **PK(id) 생성 문제가 아니다.** 두 가지를 구분해야 한다:

| 컬럼 | 성격 | 이번 사건과의 관계 |
|---|---|---|
| `article_summary.id` | PK, DB가 자동 생성(IDENTITY) | 문제 없음 — 잘 생성됨 |
| `article_summary.raw_article_id` | 기존 기사 참조(FK) + 업무 유일키 | **여기가 중복** = 같은 기사를 두 번 처리 |

즉 원인은 "id 생성"이 아니라 "같은 기사를 두 번 처리"였다.

그리고 PK 생성 자체는 **`MAX(id)+1`을 쓰면 안 된다(안티패턴).** 이유:

1. **경쟁 조건(race condition)**: 두 트랜잭션이 동시에 `MAX(id)`를 읽으면 같은 값을 얻어 둘 다 `+1` → PK 충돌. 이를 막으려면 테이블 전체 락이 필요해 동시성이 죽는다.
2. **시퀀스/IDENTITY는 원자적**: DB가 채번을 원자적으로 처리하고, 트랜잭션 롤백으로 생기는 **번호 구멍(gap)은 정상**(연속성은 보장 대상이 아님).

이 프로젝트는 `GENERATED BY DEFAULT AS IDENTITY`(Postgres identity, 내부적으로 시퀀스) + Hibernate `@GeneratedValue(strategy = IDENTITY)`를 쓴다. 이게 표준이고 안전하다.

흥미로운 점: **시퀀스 기반 id가 단조 증가**라는 성질 덕분에, 4절의 커서(`id > lastId`) 수정이 깔끔하게 성립한다. 만약 id가 무작위(UUID 등)였다면 커서 방식 대신 다른 전략(읽을 때 PROCESSING으로 선점 등)이 필요했을 것이다.

## 7. 더 나아가면 (한계와 확장)

현재 수정은 **단일 인스턴스** 기준으로 안전하다. 배치를 **여러 인스턴스로 동시 실행**하면 두 인스턴스가 같은 PENDING을 집을 수 있다. 그때의 정석:

- 읽는 순간 상태를 `PROCESSING`으로 **선점**(claim)하고 커밋 → 다른 인스턴스가 못 집게 함
  (`UPDATE ... SET status='PROCESSING' WHERE id IN (...) AND status='PENDING'` 또는 `SELECT ... FOR UPDATE SKIP LOCKED`)
- 상태 흐름을 `PENDING → PROCESSING → DONE/FAILED`로 완성 (CLAUDE.md에 정의된 라이프사이클)

v1은 단일 인스턴스라 여기까지 가지 않았고, `PROCESSING` 선점은 동시성/재시도를 다루는 v2+ 확장 과제로 남겼다.

## 8. 배운 점

- **UNIQUE 제약은 방어선이다.** 애플리케이션 로직 버그가 있어도 DB가 나쁜 데이터를 막아줬다. "설명 가능한 제약"을 걸어두는 것의 가치.
- **배치 Reader에서 "상태를 바꿔가며 그 상태로 다시 읽기"는 위험하다.** 읽기와 커밋 사이의 시간차 때문에 재조회가 처리 전 항목을 다시 물어올 수 있다. → **커서(keyset) 또는 선점(claim)** 으로 해결.
- **버그가 '꼬리 구간'에서만 나는 이유**를 이해하는 게 핵심이었다(버퍼 경계  vs 청크 경계 정렬).

- **Situation**: Spring Batch로 대량 기사를 LLM 요약·분류하는 배치를 구현.
- **Task**: 처리 배치가 남은 건이 적은 구간에서 `duplicate key`로 실패하는 문제 해결.
- **Action**: 커스텀 `ItemReader`가 "PENDING 상위 N건 재조회" 방식이라, 읽기~커밋 사이의 시간차로 아직 처리 전 항목을 재조회해 같은 기사를 한 청크에서 중복 처리함을 규명. 커서(`id > lastId`, keyset 페이지네이션) 방식으로 전환해 "한 번 읽은 id는 재조회 대상에서 제외"하도록 수정.
- **Result**: 중복 처리/제약 위반 제거. 부수적으로 UNIQUE 제약이 데이터 무결성을 지켜줬음을 확인. 다중 인스턴스 확장 시 `PROCESSING` 선점이 필요함을 한계로 문서화.

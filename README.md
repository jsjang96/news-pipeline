# news-pipeline

IT 뉴스를 수집해 LLM으로 요약·분류하고 텔레그램으로 보내는 개인 프로젝트입니다.
업무에서 다루던 Spring Batch 구조를 직접 설계해보고, 거기에 LLM API 호출 단계를
결합해보는 것을 목적으로 만들었습니다.

## 동작

| 단계 | 주기 | 하는 일 |
|---|---|---|
| 수집 | 30분 | GeekNews RSS 조회 → 신규 기사를 `PENDING` 상태로 적재 |
| 처리 | 30분 | `PENDING` 기사를 Claude API로 요약·분류하고 결과를 Redis에 캐싱 |
| 전송 | 매일 08:00 | 요약이 끝난 기사를 카테고리별로 묶어 텔레그램으로 발송 |

```
  GeekNews RSS
       │
       │  ① 수집 (30분)
       ▼
  raw_article                 status = PENDING
       │
       │  ② 처리 (30분)  Claude API 요약·분류 (+ Redis 캐시)
       ▼
  article_summary             status = DONE / notified_at = NULL
       │
       │  ③ 전송 (매일 08:00)  카테고리별 다이제스트
       ▼
  Telegram                    notified_at = 전송 시각
```

세 단계는 서로를 직접 호출하지 않고 **기사 상태로만 연결**됩니다.
각 단계는 앞 단계가 DB에 남긴 상태를 보고 자기 할 일을 찾습니다.
한 단계가 실패해도 나머지 단계는 계속 돌고, 실패한 기사는 다음 주기에 다시 대상이 됩니다.

## 결과

로컬에서 간헐적으로 운영하며 쌓인 수치입니다. (2026-08 ~ 10)

| 항목 | 값 |
|---|---|
| 수집한 기사 | 205건 |
| 요약·분류 완료 | 205건 (실패 0건) |
| 요약 평균 길이 | 132자 |

카테고리 분포

| 카테고리 | 건수 | 비율 |
|---|---|---|
| 개발 | 67 | 32.7% |
| AI | 58 | 28.3% |
| 기타 | 32 | 15.6% |
| 보안 | 31 | 15.1% |
| 클라우드·인프라 | 17 | 8.3% |

비용은 기사 1건당 약 **$0.0015** 수준입니다.
(`claude-haiku-4-5` 기준 입력 $1 / 출력 $5 per MTok, 건당 입력 약 700 · 출력 약 150 토큰)
하루 50건이 들어온다고 보면 월 2~3달러 정도이고, `max-tokens: 300`으로
출력 길이에 상한을 둬 건당 비용이 튀지 않도록 했습니다.

## 기술 스택

- Java 21, Spring Boot 4.1, Spring Batch 6, Spring Data JPA
- PostgreSQL 16 — 스키마는 Flyway로 관리 (배치 메타 테이블 포함)
- Redis 7 — 요약 결과 캐시
- Claude API (`claude-haiku-4-5`), Telegram Bot API
- Gradle, Docker Compose

## 실행

**1. 로컬 인프라 기동**

```bash
docker compose up -d
```

PostgreSQL(5432)과 Redis(6379)가 뜹니다. 끌 때는 `docker compose down`,
데이터까지 지우려면 `docker compose down -v`.

**2. 환경변수 설정**

```bash
cp .env.example .env
```

`.env`에 값을 채웁니다.

| 변수 | 설명 |
|---|---|
| `ANTHROPIC_API_KEY` | 기사 요약·분류에 사용 |
| `TELEGRAM_BOT_TOKEN` | @BotFather에서 발급 |
| `TELEGRAM_CHAT_ID` | @userinfobot에게 말을 걸면 확인 가능 (그룹으로 받으려면 그룹 id) |

**3. 애플리케이션 실행**

```bash
./gradlew bootRun
```

`.env`는 `spring.config.import`로 읽어들이므로 별도 export 없이 실행됩니다.

## 설계 메모

**단계를 상태로 분리했습니다.**
수집·요약·전송을 하나의 흐름으로 묶지 않고 기사 상태로 나눴습니다.
LLM 호출이나 텔레그램 전송이 실패해도 수집은 계속되고, 실패분만 다음 주기에 다시 처리됩니다.
실제로 API 키를 설정하지 않고 돌렸을 때 수집은 정상 동작하고 처리 단계만 멈춰 있다가,
키를 넣은 뒤 밀린 기사부터 이어서 처리됐습니다.

**스케줄러 스레드 풀을 분리했습니다.**
`task.scheduling.pool.size: 3`으로 두어 세 스케줄러가 서로 블로킹되지 않게 했습니다.

**호출 횟수를 줄이려고 주기를 다시 잡았습니다.**
처음에는 수집·처리를 10분, 전송을 3분 주기로 돌렸습니다. 뉴스가 실시간으로 반응해야 하는
성격이 아닌데 스케줄러가 하루에 수백 번씩 깨어나고 있어서, 수집·처리는 30분으로 늘리고
전송은 아침 8시 한 번으로 바꿨습니다. 하루 기준 수집·처리는 144회에서 48회로,
전송은 480회에서 1회로 줄었습니다.
수집만은 더 늘리지 않았는데, RSS가 최신 50건만 보관하고 있어 간격을 너무 벌리면
그 사이 밀려난 기사를 놓치기 때문입니다.

**하루치를 한 번에 묶어 보냅니다.**
기사 1건당 메시지 1개로 보내면 하루치가 쌓였을 때 알림이 수십 번 울리고,
텔레그램의 분당 전송 제한에도 걸립니다. 미전송 요약을 카테고리별로 묶고
한 메시지 상한(4096자)에 맞춰 나눠 보냅니다. 메시지마다 거기 담긴 기사 id를 함께 들고 있어서,
전송에 성공한 메시지의 기사만 전송 완료로 기록합니다.

**같은 본문을 다시 요약하지 않습니다.**
요약 결과를 Redis에 캐싱(TTL 7일)해 중복 호출을 막습니다.
본문 해시를 키로 쓰기 때문에, URL 중복 검사가 걸러내지 못하는
"주소는 다른데 내용이 같은" 경우도 API 호출 없이 넘어갑니다.

**조회 캐시는 넣지 않았습니다.**
Redis를 붙인 김에 조회 API에도 캐시를 넣을까 했지만, 데이터가 수백 건이고 트래픽도 거의 없어
얻는 게 없는 반면, 기사 목록은 계속 늘어나는 데이터라 캐시 무효화를 신경 써야 합니다.
LLM 호출처럼 "비싸고 변하지 않는 것"에만 캐시를 두고, 조회는 필요해지면 넣기로 했습니다.

**Spring Batch 6의 기본값을 바꿔야 했습니다.**
Batch 6부터 JobRepository 기본 구현이 인메모리(`ResourcelessJobRepository`)로 바뀌어,
그대로 두면 Job이 정상 완료돼도 실행 이력이 DB에 남지 않습니다.
`@EnableBatchProcessing`과 `@EnableJdbcJobRepository`를 함께 선언해 JDBC 기반으로 돌리고,
배치 메타 테이블도 Flyway 마이그레이션으로 관리합니다.

**기동 시 자동 실행을 껐습니다.**
`batch.job.enabled: false`로 애플리케이션이 뜰 때 Job이 자동 실행되지 않게 하고,
스케줄러를 통해서만 실행되도록 했습니다.

**비밀값은 코드에 두지 않습니다.**
API 키와 토큰은 환경변수로만 주입하며, `.env`는 커밋에서 제외하고 `.env.example` 템플릿만 추적합니다.
키가 비어 있으면 해당 단계의 스케줄러가 실행 자체를 건너뛰어, 인증 실패로 기사가
무더기로 실패 처리되는 일이 없게 했습니다.

## 트러블슈팅

개발 중 겪은 문제는 `docs/troubleshooting/`에 기록하고 있습니다.

**#001 — 같은 기사가 두 번 처리되어 UNIQUE 제약 위반**

처리 배치의 Reader가 "`PENDING` 상위 N건"을 다시 조회하는 방식이었습니다.
Spring Batch는 `read → process → write` 순서로 돌기 때문에, 읽은 직후에는 아직 상태가
`PENDING` 그대로입니다. 버퍼 경계가 청크 중간에 걸리면 방금 읽은 기사가 재조회에 다시 딸려와,
한 청크에서 같은 기사를 두 번 처리하고 요약을 중복 INSERT했습니다.
대량 구간에서는 버퍼와 청크 경계가 맞아떨어져 드러나지 않다가, 남은 건수가 청크보다 적어지는
구간에서 재현됐습니다.

커서 방식(`status = PENDING AND id > lastId`)으로 바꿔 한 번 읽은 id는 다시 조회되지 않도록
해결했습니다. 잘못된 데이터가 저장되지 않은 것은 `article_summary`에 걸어둔 UNIQUE 제약
덕분이었고, 실패한 청크는 통째로 롤백돼 정합성은 유지됐습니다.

→ [상세 기록](docs/troubleshooting/001-batch-reader-duplicate-summary.md)
